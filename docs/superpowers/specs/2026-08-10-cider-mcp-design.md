# Cider MCP — Design and Rationale

`cider-mcp` is an MCP server that lets an agent drive [Cider 4](https://cider.sh) on
macOS: playback, queue, library, catalog search, and playlist creation.

This document records **why the server is built the way it is**. The decisions below
are already made and shipped; each one is anchored to the API behaviour that forced
it. For installation and usage see `README.md`; for the task-by-task build order see
`docs/superpowers/plans/2026-08-10-cider-mcp.md`.

**Verified against:** Cider 4.0.0 on macOS, targeting MCP specification 2026-07-28.

Every API claim carries its evidence, labelled either *(verified live)* — an HTTP
call against a running Cider — or *(source)* — read out of Cider's shipped Electron
bundle (`Cider.app/Contents/Resources/app.asar`, main-process file under
`.vite/build/main-*.js`). None of it comes from Cider's public API documentation,
which describes only the older v1 surface and is wrong in at least one material
respect (queue index base). Where a finding is enforced in code, the tables name the
file — those are the places an innocent-looking change breaks things silently.

## Goals

Queue control, playback control, and playlist creation, driven by an agent, from
both Claude Code and Claude Desktop.

## Non-goals

- Deleting or reordering playlists — structurally impossible, see
  [Verified API behaviour](#verified-api-behaviour).
- Running without Cider open. Cider is the auth and playback substrate.
- Taste heuristics in server code. Tools are primitives; judgment belongs to the model.

## Protocol baseline

Targets MCP specification **2026-07-28** via `@modelcontextprotocol/server` ^2.0.0,
the Tier-1 TypeScript SDK for that revision. Not `@modelcontextprotocol/sdk` v1.x,
which implements the superseded line.

Consequences for this server:

- **Log to stderr only.** The Logging feature is deprecated (SEP-2577), and stdout
  is the JSON-RPC channel.
- **`inputSchema` must be a `z.object(...)`.** Raw-shape registration is deprecated.
- **`tools/list` order must be deterministic** — a SHOULD in the spec, and it
  improves client-side cache hits. One frozen, ordered array in `src/tools/index.ts`
  is the single source of that order.
- **Serve with `serveStdio(factory)`, not a hand-wired transport.** On stdio,
  `serveStdio` classifies the opening exchange and pins a 2026-07-28-era instance;
  `McpServer` exposes no era option, so hand-wiring silently serves the legacy era
  (`src/index.ts`).
- Sessions and the `initialize` handshake are gone. Nothing here holds cross-request
  state, so that costs this server nothing; it reinforces the
  fetch-tokens-per-process rule below rather than conflicting with it.
- Tools carry `annotations` (`readOnlyHint`, `destructiveHint`, `idempotentHint`) so
  clients can reason about blast radius.

## Architecture

One TypeScript stdio process. Two HTTP clients behind one tool layer.

```
                      ┌─ CiderClient ──────► localhost:10767/api/v2/*
  MCP tool layer ─────┤                      header: apptoken: <24-char>
  (stdio)             │                      playback · queue · library · audio
                      │
                      └─ AppleMusicClient ─► api.music.apple.com/v1/*
                                             Authorization: Bearer <developerToken>
                                             Music-User-Token: <userToken>
                                             Origin: https://music.apple.com
                                             catalog search · playlist writes
```

The split is forced, not stylistic: Cider exposes **no search endpoint and no
playlist-create endpoint**. Anything involving discovery or playlist mutation must
go direct to Apple, using MusicKit tokens borrowed from Cider.

### Why not a Cider plugin

Considered and rejected. A PluginKit plugin can reach
`window.CiderApp.musicKitStore.addToPlaylist`, but plugins only live while Cider's
window is open, cannot host a server, and would still need a stdio shim — two
processes instead of one, for a capability the Apple Music API already provides
directly. An existing third-party Cider playlist-sync plugin takes exactly that
path and documents the same lifecycle limitation in its own README.

## Auth

### Cider app token

Acquired in four tiers, in order (`src/token.ts`):

1. **macOS Keychain** — `security find-generic-password`, service `cider-mcp`,
   account `app-token`. This is the steady state after the first successful run.
2. **`CIDER_APP_TOKEN` environment variable**, for a token generated by hand under
   Settings → Connectivity → Manage External Application Access. It is written to
   the Keychain on first use, so it is needed only once.
3. **Pairing** — `POST /api/v2/auth/request` with `{app_name, scopes[]}`. This pops
   an approval dialog inside Cider and returns `{data: {token, scopes}}`.
4. **Config-file recovery** — if the pairing response is lost, read the token from
   `~/Library/Application Support/sh.cider.genten/spa-config.yml` under
   `connectivity.apiTokens[]`, matching on `name`.

The pairing request deliberately carries **no client-side timeout**. Cider bounds the
wait itself (~120 s, then `408 AUTH_REQUEST_TIMEOUT`), and a short client timeout
creates the one failure mode observed in testing: the client gives up, the user
approves anyway, and a valid token is minted that the client never sees. Tier 4
exists for exactly that race — the token is already on disk by then.

Scopes requested: `playback`, `queue`, `library`, `audio`, `account`.
`account` is required — it is the only thing that yields MusicKit tokens — and it
hands out a real credential, so it is called out explicitly in the README rather
than buried.

### Storing the app token

The Keychain, never a dotfile. The write goes through `security add-generic-password`
(`src/keychain.ts`), which has three traps worth knowing before touching that file:

- The secret must go over **stdin, never argv**. Argv is world-readable in the
  process table for the lifetime of the call, so `-w <secret>` leaks the token to
  every local user.
- Given a bare `-w`, `security` prompts twice and expects the secret **written
  twice**. Writing it once is a silent-corruption trap: it reports "passwords don't
  match", stores an *empty* password, and still exits 0.
- Those prompts use `getpass(3)`, which reads `/dev/tty` whenever a controlling
  terminal exists. Spawned from an interactive shell the child would block on the
  terminal while the secret waits on the pipe, hanging startup forever. Spawning
  with `detached: true` (`spawn`, not `execFile` — `execFile` silently drops the
  option) puts the child in a new session with no controlling terminal, so `getpass`
  falls back to stdin.

### MusicKit tokens

`GET /api/v2/client/tokens` (scope `account`) returns
`{developerToken, userToken, storefront}`. *(verified live: token lengths ~268 and
~246, plus a two-letter storefront code.)*

**These are never persisted.** They are fetched from Cider per process and re-fetched
once on any Apple 401, then the request is retried exactly once before failing
(`src/apple-client.ts`). The developer token is nominally a 35-day credential
(`iss: AMPWebPlay`, `kid: WebPlayKid`), but the one observed in testing had roughly
12 hours of life left — Cider hands out whatever it currently holds. A design that
caches these across sessions will fail daily.

## Verified API behaviour

These are load-bearing and are not documented anywhere upstream. Each was found by
reading the shipped bundle or by live call, not by inference.

### Cider's local API (`http://localhost:10767`)

| Finding | Evidence | Enforced in |
|---|---|---|
| Queue indices are **0-based** | source: `{index: int().min(0)}`, `{from, to: int().min(0)}` — the public v1 docs say 1-based and are wrong for v2 | `src/tools/queue.ts` |
| Pagination caps at 200 | source: `limit: int().min(1).max(200).default(50)`, `offset` ≥ 0 | `src/tools/queue.ts`, `src/tools/library.ts` |
| IDs, types, hrefs and URLs reject quotes | source: every such field carries `regex(/^[^'"]+$/)`, so Cider's own API rejects quotes in them — mirror that client-side for a clear error | `assertSafeId` in `src/cider-client.ts` |
| Responses are enveloped as `{data}` or `{data, meta}` | source: a minified helper of the form `(data, meta) => meta ? {data, meta} : {data}`; every paginated handler passes `meta: {offset, limit, total}` | `CiderClient.request` in `src/cider-client.ts` |
| `POST /api/v2/playback/previous` **400s on a body-less POST** | source: unlike every other bodyless playback POST, this route unconditionally runs `z.object({force: boolean().optional()}).parse(request.body)`. With no body, `request.body` is `undefined`, the parse throws, and Cider answers `400 INVALID_REQUEST`. Always send at least `{}` | `previous_track` in `src/tools/playback.ts` |
| Pairing outlasts any sane client timeout | verified live: a client that disconnected after 140 s still caused the token to be minted and persisted; Cider's own bound is ~120 s, then `408 AUTH_REQUEST_TIMEOUT` | `src/token.ts` |
| Approved tokens appear in `spa-config.yml` with `method: auth-request-api` | verified live; each approval **appends** a new entry, so for a given app name the *last* match is the live token and earlier ones may be revoked | `tokenFromConfig` in `src/token.ts` |
| Full scope list | source: `playback\|queue\|library\|audio\|account\|plugins\|config` | `CIDER_SCOPES` in `src/token.ts` |
| Dropping `meta` loses `total` | source: paginated handlers report totals only in `meta`, so a client that unwraps `data` alone cannot tell whether more pages exist | `CiderClient.request` in `src/cider-client.ts` |

### Apple Music, using Cider's tokens

| Finding | Evidence | Enforced in |
|---|---|---|
| **`Origin: https://music.apple.com` is mandatory on every request** | verified live: an identical catalog request returns 401 with no Origin, 401 with `Origin: https://cider.sh`, 401 with `Origin: http://localhost:10767`, and 200 with `Origin: https://music.apple.com`. The developer token carries `root_https_origin: ["apple.com"]` | `REQUIRED_ORIGIN` in `src/apple-client.ts` |
| Send `Accept-Encoding: identity`, or handle gzip | verified live: Apple returned a gzipped body that crashed a naive UTF-8 decode | `src/apple-client.ts` |
| Playlist **create** works | `POST /v1/me/library/playlists` → **201** | `playlist_create` in `src/tools/playlists.ts` |
| Playlist **append** works | `POST /v1/me/library/playlists/{id}/tracks` → **204** | `playlist_add_tracks` in `src/tools/playlists.ts` |
| Playlist **delete** does not | `DELETE /v1/me/library/playlists/{id}` → **401**, under standard headers, without `Origin`, and with the user token alone | deliberately no tool |

### Playlist writes are one-way

The delete limitation is surfaced, not hidden. There is no `playlist_delete`,
`playlist_remove_track`, or `playlist_reorder` tool, because none of them can work
with the credential Cider holds; both playlist tools say so in their own
descriptions, and the server documents that deletion happens in Cider's UI.

The consequence is worth stating plainly: **every playlist an agent creates through
this server is an artifact only a human can remove.** A mistaken or half-finished
playlist has to be cleaned up by hand in Cider. That is precisely why the missing
operations are absent rather than exposed and left to fail at runtime. The live
smoke check (`scripts/smoke.ts`) shows the shape of it — it creates a playlist,
cannot tear it down, and prints the id with instructions to delete it in Cider
instead of pretending to clean up after itself.

## Tool surface

Thin primitives, ~1:1 with endpoints, 35 in total. The model composes them.

**Playback and audio** (16, `src/tools/playback.ts`) — `now_playing`,
`playback_state`, `play`, `pause`, `toggle_playback`, `next_track`,
`previous_track {force?}`, `seek {position}`, `set_repeat {mode: none|one|all}`,
`set_shuffle {enabled}`, `set_rating {rating: -1|0|1}`, `play_item {type, id}`,
`play_collection {type, id, shuffle?}`, `get_volume`,
`set_volume {volume: 0..1}`

A `play_url {url}` tool is part of the design but is held out of the initial
release — it forwards a free-form, model-chosen URL to Cider, and out of caution
around handing the player an arbitrary URL it waits on further review. It lives
on the `feature/play-url` branch. See the README.

**Queue** (8, `src/tools/queue.ts`) — `queue_list {offset, limit}`, `queue_position`,
`queue_add_next {type, id}`, `queue_add_later {type, id}`, `queue_jump {index}`,
`queue_move {from, to}`, `queue_remove {index}`, `queue_clear {confirm: true}`

**Library** (7, `src/tools/library.ts`) — `library_playlists`,
`library_playlist_tracks {id}`, `library_albums`, `library_album_tracks {id}`,
`library_artists`, `library_songs`, `library_add_current`

**Discovery, Apple direct** (2, `src/tools/discovery.ts`) —
`catalog_search {term, types, limit}`, `recently_played {limit}`

**Playlists, Apple direct** (2, `src/tools/playlists.ts`) —
`playlist_create {name, description?, track_ids[]}`,
`playlist_add_tracks {playlist_id, track_ids[]}`

Two rules hold across the surface:

- **`queue_clear` requires an explicit `confirm: true`.** It is the only tool that
  destroys user state irrecoverably, and an agent should have to mean it.
- **Annotations are mandatory in practice, not decorative.** MCP treats an *absent*
  `destructiveHint` as `true`, so an unannotated `queue_add_next` would read to a
  client as more dangerous than `queue_clear`. Every mutating tool states its hints
  explicitly. `play_item` and `play_collection` are annotated
  `destructiveHint: true` because they replace the queue, unlike `play`/`pause`/
  `seek`, which only move within it.

## Error handling

Cider's structured error codes are mapped to actionable messages rather than leaking
HTTP status (`src/errors.ts`):

| Code | Message |
|---|---|
| `UNAUTHORIZED_APP_TOKEN` | Token invalid or revoked — re-pair. |
| `INSUFFICIENT_SCOPE` | Names the missing scope and how to re-grant it. |
| `RPC_TIMEOUT` | Cider's renderer did not respond; retry. |
| `AUTH_REQUEST_BUSY` | A pairing dialog is already open in Cider. |
| `AUTH_REQUEST_TIMEOUT` | Cider closed the dialog unanswered; restart and approve promptly. |
| `AUTH_REQUEST_DENIED` | Access was declined in Cider. |
| `APPLE_UNAUTHORIZED` | Apple rejected it — expired token, or an operation that is never permitted (playlist deletion). |
| `CIDER_NOT_RUNNING` | Cider is not reachable on port 10767. |

Two details that are easy to get wrong:

- Node's global `fetch` (undici) rejects connection failures with a plain
  `TypeError: fetch failed`; the real `code` (`ECONNREFUSED`, …) lives one level down
  on `err.cause`. Reading only the top-level `code` mislabels "Cider isn't running"
  as an unknown failure.
- Tool failures are returned as **results** with `isError: true`, not as protocol
  errors, so the model can read the message and adjust (`src/server.ts`).

Apple 401 triggers exactly one token refresh plus retry before failing. The
abandoned 401 response body is cancelled before the retry, so undici can release the
socket instead of holding it until GC.

## Testing

- Unit tests (vitest, mocked HTTP) over both clients, the error mapper, the token
  acquisition ladder, the Keychain wrapper, and server registration. They cover the
  0-based queue math, the `Origin` header, the gzip opt-out, refresh-on-401, the
  `{data, meta}` envelope, and the "last matching entry wins" rule in
  `spa-config.yml`. Run with `pnpm test`.
- One live smoke script behind an env var: `CIDER_MCP_SMOKE=1 pnpm smoke`. It
  **cannot self-clean** — playlist delete 401s — so it prints the created playlist
  id for manual removal rather than pretending to tear down. It writes to a real
  Apple Music library, which is why it is env-gated.

## Questions the implementation settled

- **Where library reads come from.** All seven `library_*` tools go through Cider's
  own v2 API (`/api/v2/library/*`), spending no Apple credentials. Only what Cider
  cannot serve goes direct to Apple: catalog search, recently played, and playlist
  create/append.
- **Token acquisition order.** The original design tried pairing first. The shipped
  order puts the Keychain first and the environment variable second, so the common
  case involves no dialog and no network, and pairing is reached only on a genuinely
  cold start.
- **Packaging.** No bundler. `tsc` emits `dist/`, and clients launch
  `node <repo>/dist/index.js` — the same command for Claude Code and Claude Desktop.
  The package is `private` with a `bin` entry (`cider-mcp`) for local linking rather
  than npm publication.

## Still unverified: `queue_move` semantics

`POST /api/v2/queue/move` takes `{from, to}`, both constrained to `int().min(0)` in
Cider's schema. Whether `to` is interpreted **before or after** the source item is
lifted out of the list has never been confirmed against a live queue. The two
readings disagree whenever an item moves downward: pre-removal semantics land it one
slot later than post-removal semantics.

`queue_move` passes `from` and `to` straight through (`src/tools/queue.ts`), which is
faithful to the schema and agnostic about the answer. This is the only tool in the
server whose behaviour is inferred rather than observed, and the README says so as
well. To settle it: list the queue, move index 0 to index 3, list again, and compare
against both predictions. If an adjustment is needed it belongs in the tool handler,
and the tool description should then state which convention callers get.
